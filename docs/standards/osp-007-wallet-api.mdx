The wallet is the only component that holds keys. This draft defines the API
everyone else uses to interact with it, without ever seeing the keys.

## Summary

The wallet service owns the key hierarchy and exposes a narrow API: derive
addresses, sign under consent, submit transactions, and manage recovery. No
other component ever holds or sees private keys. The reference design is the
[Wallet Architecture](/docs/technical-design/wallet-architecture) page.

## Purpose

Keys are the root of identity and value. The wallet API exists so that key
operations are centralized, consent gated and auditable, instead of spread
across every application.

## Example

A signing request as defined by this draft:

```json
{
  "method": "wallet.sign",
  "params": {
    "payload": "0x7a3f...",
    "purpose": "authentication"
  },
  "id": 42
}
```

The exact method names, parameter schemas and error codes are normative content
under review.

## Implementation status

The reference implementation includes the wallet service, key hierarchy and
consent gated signing. The draft tracks the design at 0.1.0. No conformance
suite has been published yet.
