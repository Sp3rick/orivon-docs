The standards program is deliberate: drafts first, review, then acceptance, and
only then the machinery of certification. This page lays out where the program
is, where it is going, and what it will take to get there.

## Where the program is

The current state in one view:

  <Stat value="15" label="Drafts published" />
  <Stat value="0" label="Accepted" />
  <Stat value="0" label="Conformance suites shipped" />

Every specification is a 0.1.0 draft. The program is in the phase where the
drafts are being hardened against the reference implementation. See
[Draft Specifications](/docs/standards/draft-specifications).

## Sequencing logic

The order is not arbitrary. It follows dependencies:

<Diagram caption="The dependency order of the standards work.">
  <Flow column>
    <DiagramNode accent>Foundations (runtime, core, modules)</DiagramNode>
    <FlowArrowDown />
    <DiagramNode>Surfaces (wallet, identity, permissions)</DiagramNode>
    <FlowArrowDown />
    <DiagramNode>Network and data (networking, storage, events)</DiagramNode>
    <FlowArrowDown />
    <DiagramNode dim>Tooling (SDK, conformance, CLI)</DiagramNode>
  </Flow>
</Diagram>

Each layer must be accepted before the layer that builds on it can be
meaningfully certified. The [draft series](/docs/standards/draft-specifications)
already reflects this order in its numbering.

## What could change the plan

Roadmaps are plans, not prophecies. The plan adjusts when:

<CardGrid columns={2}>
  <Card title="Implementation learns">
    If the reference implementation reveals a design gap, the affected draft is
    revised before acceptance.
  </Card>
  <Card title="Community priorities shift">
    Heavily requested categories can move earlier in the plan.
  </Card>
  <Card title="Specifications converge">
    Adjacent drafts may merge, which changes the sequence.
  </Card>
  <Card title="Security demands">
    A security finding can pull a security or cryptography specification
    forward.
  </Card>
</CardGrid>

The lifecycle gates in [Specification Lifecycle](/docs/standards/specification-lifecycle)
are the mechanism that absorbs these changes without chaos.

## How to help

The roadmap is public and participation is open:

- **Review drafts** and file issues against their normative text.
- **Test assumptions** by building against a draft and reporting what breaks.
- **Propose changes** through the lifecycle, from idea to draft.
- **Contribute to conformance** when the framework ships.

The [overview](/docs/standards/overview) explains the contribution process from
start to finish.

<Callout type="success" title="Definition of done for the program">
  The standards program is mature when the foundations are Accepted, the
  conformance framework ships, and a third party can implement, certify and
  interoperate using only public documents.
</Callout>
